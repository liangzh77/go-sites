# Provider / Key 管理台执行方案

> 状态：已部署到 `https://liangz77.cn/keys/`，线上服务与备份检查通过。
> 本轮授权范围：按用户指示实施、测试、提交、推送并部署；不调用任何真实 Provider。

## 一、目标与范围

在 `/private` 增加「API 密钥管理」入口，指向：

**https://liangz77.cn/keys/**

第一版按以下默认需求设计：

- 单人私有使用，服务端保存，支持跨设备访问。
- 一个 Provider 配置可以拥有多个 Key。
- 同一厂商可以建立多个配置，分别管理官方、国际站、Coding Plan、中转站等入口。
- 手动检测单个 Key、某个 Provider 或全部启用的 Key。
- 支持备注、预计到期日、到期提示。
- 支持模型配置及不同模型的参数差异。

**第一版不做：**聊天界面、请求中转、自动轮询、自动续费、外部通知、多用户协作。余额与套餐查询只在厂商有可靠接口时提供。

## 二、页面与交互

### 1. 主页面

顶部提供：

- 新增 Provider。
- 搜索：名称、Key 别名、备注。
- 筛选：Provider、检测状态、即将到期、已停用。
- 批量刷新。

Provider 分组展示，展开后显示所属 Key：

| 字段 | 内容 |
| --- | --- |
| 别名 | 例如“官方主用”“月付备用” |
| 密钥 | 默认脱敏 |
| 测试模型 | 最近使用或指定的模型 |
| 检测状态 | 成功、认证失败、限流等 |
| 最近检测 | 时间和耗时 |
| 预计到期 | 日期、剩余天数 |
| 备注 | 简短摘要 |
| 操作 | 编辑、刷新、显示／复制、停用、删除 |

### 2. 配置表单

**Provider：**

- 显示名称、厂商预设、接口协议、API 地址、备注。
- 官方／国际站／Coding Plan 等入口独立选择，不默认混用。
- 自定义 Provider 支持填写地址、选择协议和认证方式。

**Key：**

- 别名、密钥、启用状态、测试模型。
- 购买日期、预计到期日、提前提醒天数。
- 自由备注。

**模型：**

- 模型 ID、上下文上限、最大输出。
- 是否支持思考、思考等级／预算及相关参数。
- 默认测试配置。
- 参数来源、更新时间，支持手动覆盖。

删除只影响本站记录，不撤销厂商密钥。删除包含多个 Key 的 Provider 时，明确提示影响范围。

## 三、Provider 适配方案

### 1. 首批范围

| 类别 | Provider |
| --- | --- |
| 国际官方 | OpenAI、Anthropic、Google Gemini、xAI、Mistral |
| 国内官方 | DeepSeek、阿里百炼、火山方舟、Moonshot/Kimi、智谱、MiniMax、百度千帆、腾讯混元 |
| 聚合／推理平台 | OpenRouter、硅基流动、Groq、Together AI、Fireworks |
| 自定义协议 | OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini |

Azure OpenAI、AWS Bedrock、Vertex AI 暂不列入第一版承诺，后续单独适配其部署、区域和身份认证机制。

### 2. 实现原则

采用三层结构：

1. **协议适配器**：认证、请求、响应解析。
2. **厂商配置**：地址、特殊字段、错误识别、模型发现方式。
3. **模型能力配置**：思考参数、上下文和输出限制。

实施时逐项核对官方文档，不能只增加一个厂商名称就算支持。

模型列表优先通过接口获取；不支持时允许手动添加。**上下文与思考能力不从模型名称猜测**，也不通过大额测试请求试探；未知信息明确标记为未知。

## 四、刷新与状态判定

### 1. 检测流程

1. 校验 Provider 地址、Key 和测试参数。
2. 使用选定模型发送一次小规模真实请求。
3. 限制超时、输出预算和批量并发。
4. 保存检测结果、模型、时间、耗时及脱敏错误摘要。
5. 更新列表，不自动进行可能重复计费的重试。

首次真实检测说明可能产生少量费用；批量检测展示数量并确认。停用的 Key 默认跳过。

### 2. 状态分类

- 未检测。
- 调用成功。
- 认证失败。
- 余额／额度不足。
- 限流。
- 模型不存在／无权限。
- 参数不兼容。
- 网络／服务异常。
- 未知错误。

判定不足时保留“不确定”，不把所有失败归为“密钥失效”。

此外：

- 状态对应**当时的 Key、地址、模型及参数**。
- 配置修改后，旧结果标记为过期，等待重新检测。
- 并发检测不能让旧结果覆盖新配置的状态。
- 预计到期与检测状态独立展示。
- 明确检测来自网站服务器，不代表用户本机网络。

## 五、后端、存储与安全

### 1. 结构建议

新增独立 Go 服务，避免把密钥管理逻辑混入演示管理功能：

| 路径 | 计划用途 |
| --- | --- |
| `cmd/keys/` | 后端、Provider 适配、检测和测试 |
| `cmd/keys/web/` | 管理页面 |
| `data.js` | `/private` 的入口条目 |
| `Caddyfile` | `/keys/` 及接口路由 |
| `docs/keys.md` | 使用、配置、部署和恢复说明 |

使用 SQLite 保存 Provider、Key、模型配置和有限的检测历史。数据库放在独立持久化目录，不随代码发布覆盖。

### 2. 安全要求

- 页面和全部接口均进行服务端鉴权，不信任浏览器的“已登录”标记。
- 核查并加固现有登录机制，禁止依赖静态文件中的密码。
- 密钥及敏感认证字段加密落库；加密主密钥独立保管。
- 缺少加密主密钥时拒绝启动密钥服务。
- 列表不返回完整密钥；显示／复制完整密钥需要重新认证。
- 禁止将密钥写入日志、URL、静态资源或浏览器持久存储。
- 敏感响应禁止缓存，修改接口具有 CSRF 防护。
- 自定义地址必须防范内网访问、DNS 重绑定及跨域重定向泄密。
- 密钥业务仅通过 HTTPS 使用。
- 数据库与加密主密钥分别制定备份、恢复方式。

**上线前必须解决的额外检查：**现有站点支持上传 HTML 演示，需要确认其脚本是否与密钥页面同源。若存在不可信同源脚本，必须先完成可靠隔离；仅设置 HttpOnly 或不同路径不足以保护密钥。

### 阶段 1：确认接口与安全边界

### 阶段 2：完成管理基础

- Provider / Key / 模型配置的增删改查。

### 阶段 3：完成检测能力

- 通用协议适配。
- 厂商差异化处理。
- 单个与批量检测、错误分类、检测历史。

### 阶段 4：前端集成

- 完成桌面与手机布局。
- 添加 `/private` 入口。
- 完成表单校验、危险操作确认和状态反馈。

### 阶段 5：测试与发布准备

- 自动化测试、安全检查、授权后的真实联调。
- 编写部署、备份和回滚说明。
- 完成验收后，再单独确认是否部署。

## 七、验收标准

### 1. 功能

- 一个 Provider 可管理多个 Key，同厂商可创建多个实例。
- 增删改和备注保存后，重启服务仍保留。
- 模型参数按能力展示与校验，不向不支持的模型盲目发送参数。
- 刷新结果可追溯到具体模型、时间和配置。
- 到期提醒不冒充真实失效判定。

### 2. 安全

- 未登录无法读取数据、执行检测或取得完整密钥。
- 数据库中的密钥为密文，日志和普通接口不泄露密钥。
- 自定义地址不能访问服务器内网或将凭据带到其他主机。
- 同源内容风险已处理。
- 备份恢复与发布回滚经过验证。

### 3. Provider 验证

- 自动化测试覆盖各适配器的请求格式和错误响应。
- 有授权测试 Key 的 Provider，再做真实联调。
- 没有测试 Key 的明确标注“协议测试通过，待真实联调”，不宣称已实测。
- 不擅自读取其他项目中的凭据进行验证。
